# Аудит портфеля ИТ-проектов

ETL и SQL-аналитика по трём несвязанным выгрузкам (PMO, ИТ-департамент, финансовый учёт): нормализация данных, загрузка в Postgres и аналитика по срокам, бюджетам и ИТ-ландшафту. Полная постановка задачи — [`docs/task_description.md`](docs/task_description.md).

## Структура репозитория

```
.
├── docker-compose.yml   # Postgres для проверки результатов без своей БД
├── data/raw/            # исходные выгрузки как есть (3 xlsx)
├── docs/
│   ├── task_description.docx  # ТЗ, оригинал
│   ├── task_description.md    # ТЗ, читаемая версия
│   ├── findings.md             # выводы по качеству данных + бонусный анализ
│   └── presentation_plan.md     # план итоговой презентации по слайдам
├── etl/
│   ├── config.py        # пути к файлам, подключение к БД, курс валют
│   ├── normalize.py     # нормализация кодов проектов, дат, сумм
│   ├── extract.py       # чтение xlsx -> нормализованные строки
│   ├── load.py           # создание схемы и запись в Postgres
│   └── main.py            # точка входа: связывает всё вместе (запускать этот файл)
├── sql/
│   ├── create_tables.sql   # схема БД
│   ├── analysis.sql         # обязательная аналитика по разделам ТЗ
│   └── bonus_analysis.sql    # аналитика вне ТЗ (см. docs/findings.md)
└── charts/
    ├── config.py         # подключение к БД, каталог вывода
    ├── style.py           # палитра и оформление осей (единый стиль графиков)
    ├── queries.py          # выборки из БД для графиков (зеркало sql/*.sql)
    ├── data_quality.py      # аномалии из сырых xlsx (для слайда о качестве данных)
    ├── plots.py              # рендер каждого графика в SVG
    ├── main.py                # точка входа: строит все графики (запускать этот файл)
    └── output/                 # сюда сохраняются SVG + kpi_summary.txt (не в git)
```

Пайплайн линейный: `data/raw/*.xlsx` → `etl/main.py` (создаёт схему из `sql/create_tables.sql` и грузит данные) → Postgres → `sql/analysis.sql` → `charts/main.py` (графики для презентации).

## Как повторить

Нужен Postgres. Если своего нет, но установлен Docker — поднимите его командой ниже, конфигурация в `docker-compose.yml` совпадает с дефолтами `etl/main.py`, поэтому переменные окружения задавать не придётся:

```bash
docker compose up -d          # поднимет Postgres на localhost:5432 (db=myapp, user=postgres, password=secret)
docker compose ps             # дождаться статуса "healthy"
```

Если своя БД уже есть — просто задайте параметры подключения через переменные окружения (ниже — те же значения, что и дефолты в `main.py`, при своей БД замените их на реальные):

```bash
export PGHOST=localhost PGPORT=5432 PGDATABASE=myapp PGUSER=postgres PGPASSWORD=secret
```

Дальше в любом случае:

```bash
pip install -r requirements.txt
python etl/main.py          # создаёт таблицы (если их нет) и заливает данные; можно запускать повторно
psql -f sql/analysis.sql       # либо выполнить запросы по одному через любой SQL-клиент
```

Скрипт идемпотентен: перед загрузкой таблицы очищаются (`TRUNCATE ... RESTART IDENTITY`), так что повторный запуск не даёт дублей.

Чтобы полностью остановить и удалить поднятую через Docker БД вместе с данными: `docker compose down -v`.

## Графики для презентации

```bash
python charts/main.py
```

Требует уже загруженную БД (шаг выше). Кладёт в `charts/output/` 9 SVG (по одному на каждый график из `docs/presentation_plan.md`) и `kpi_summary.txt` с готовыми цифрами для текстовых плашек слайда 1.

Графики рендерятся **без заголовков, легенд-подписей слайда и фона** (прозрачный SVG) — это самостоятельные "куски" для сборки, не готовые слайды. Дальше:

1. Импортировать SVG-файлы в Figma как изображения (drag & drop) — это векторы, масштабируются без потери качества.
2. Разложить по артбордам (1 артборд = 1 слайд) по структуре из `docs/presentation_plan.md`, добавить заголовки, KPI-плашки из `kpi_summary.txt`, выводы — уже средствами Figma.
3. Экспортировать готовые артборды в PDF (`File → Export`, можно выбрать сразу несколько фреймов).

Палитра и оформление графиков — по методичке skill'а dataviz (`charts/style.py`): фиксированный порядок цветов, разряженная сетка, подписи вместо легенды там, где это возможно.

## Качество исходных данных и что было исправлено

При загрузке (`etl/main.py`) обнаружены и обработаны:

- **Битые коды проектов** — 17 строк (15 уникальных значений) в `it_landscape.xlsx` вида `PRJ001` вместо `PRJ-001`, разбросаны по всему файлу. Нормализуются под единый формат `PRJ-NNN` перед связыванием с `projects`.
- **Разные форматы дат** — `projects_schedule.xlsx` в `DD.MM.YYYY`, `projects_budgets.xlsx` — смесь `YYYY-MM-DD` и `YYYY/MM/DD`. Приводятся к единому `DATE`.
- **"Грязные" суммы** — 30 строк в `projects_budgets.xlsx` — строки вида `"380 675 руб"` вместо чисел, разбираются отдельным парсером.
- **Даты-заглушки в расписании** — 10 значений `fact_end` в `project_tasks` отклоняются от `plan_start` своей же задачи на 1867–2252 дней (~5-6 лет) в прошлое. Начать или закончить задачу раньше плана — это нормально и в данных встречается часто (максимум реального опережения — 2 дня), поэтому заглушки отсеиваются не по самому факту "раньше плана", а по неправдоподобному масштабу отклонения (запас — год, `IMPLAUSIBLE_EARLY_MARGIN_DAYS` в `etl/extract.py`). Такие значения заменяются на `NULL`.
- **Валюта** — суммы платежей приводятся к рублю по фиксированному курсу (1 USD = 90 RUB, 1 EUR = 100 RUB) в поле `amount_rub`.

Отдельно, уже на уровне SQL (`sql/analysis.sql`, раздел 1.3), выявлены две логические ошибки ведения плана, которые ETL не исправляет автоматически, а помечает для ручного разбора:

- 15 задач помечены завершёнными (`fact_end` задан), но не имеют даты начала (`fact_start` пуст).
- 6 задач ещё не завершены, хотя более поздняя по плану задача того же проекта уже завершена — нарушение последовательности выполнения. Именно эти 6 строк, вместе с ещё 4 такими же по своей природе (но пришедшимися на последнюю задачу проекта — "Финальный релиз"), и составляют те самые 10 строк с датой-заглушкой выше.

Полный разбор качества данных с рекомендациями для систем-источников и бонусный анализ поверх нормализованных данных (за рамками ТЗ) — **[`docs/findings.md`](docs/findings.md)**. План итоговой презентации (слайды, графики, источники данных) — **[`docs/presentation_plan.md`](docs/presentation_plan.md)**.

## Что считает `sql/analysis.sql`

| Раздел ТЗ | Запросы |
|---|---|
| Анализ расписания | плановая/фактическая длительность каждой задачи; топ-5 проектов по срыву дедлайна; 2 запроса на логические ошибки ведения плана (см. выше) |
| Финансово-ресурсный анализ | общая стоимость портфеля и средняя стоимость проекта; топ-3 PM по объёму освоенного бюджета |
| Бизнес-анализ ИТ-ландшафта | категоризация проектов на "Технологические"/"Офисно-коммерческие" + сравнение среднего бюджета и средней задержки между группами |

Плюс `sql/bonus_analysis.sql` — аналитика вне ТЗ (бенчмарк этапов, надёжность PM по срокам, валютная структура портфеля, полнота выполнения). Разбор — `docs/findings.md`, раздел 2.
